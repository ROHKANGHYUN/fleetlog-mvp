# Fleetlog MVP 2 · 모의 대화와 자동 운행 전달

현재 전체 MVP의 보완·월별 자료·CSV·모의 접수·GitHub 준비 결과는 [최종 인수인계](MVP_FINAL_HANDOFF.md)를 기준으로 합니다. 이 문서의 과거 테스트 수치는 해당 단계의 실행 이력입니다.
최신 변경은 [MVP 차량 UI 업데이트](MVP_VEHICLE_UI_UPDATE.md)를 기준으로 합니다. 이전의 **연결 후 항상 빈 화면·출발 전 질문·도착 즉시 확정**은 최신 사용자 요구로 대체했습니다. 아래 실행 결과 표의 214개/30개는 2단계 당시의 검증 이력입니다.

검증일: **2026-11-15 KST**. 현재 흐름은 QR 또는 코드 연결→모의 출발→주차 관측→차량 운행 마치기→질문/초안/재확인→사용자 동의 또는 미확정 보관→자동 HTTP 수신입니다. 차량 화면은 주차 중 표시하고 주행 중 비웁니다. 실제 STT·마이크·Pleos·Android·실차 수집·운영 인증·세무 기능은 추가하지 않았습니다.

## 구현 흐름과 경계

```text
QR/대체 코드 명시적 연결 (질문·운행 생성 없음)
  → 명시적 모의 출발 (운전자·연결·원본 시작 고정, 차량 화면 비움)
  → 모의 도착 (주차 관측·구간 표시만, 저장/질문 없음)
  → 차량의 운행 마치기 (종료 후보 시각·거리 고정)
  → 시연 패널 안내 완료 → 모의 답변 초안 → 재확인 안내 → 모의 네
     또는 무응답·실패·나중에 (목적 null)
  → 종료 원본 + 준비된 이벤트 함께 저장
  → 패널 자동 uploader → 실제 MVP HTTP → 수신 운행/영수증 commit
  → 모바일 직원 내역·관리자 수신 목록 자동 조회
```

**수집 대기와 수신은 같은 격리 MVP SQLite 안의 별도 테이블**입니다. 이번 MVP의 대기 저장소는 차량 장치나 브라우저의 오프라인 저장소가 아닙니다. 패널의 모의 제어 API가 수집 원본을 보관하고, 패널 uploader가 실제 수신 API에 별도로 요청합니다. 따라서 업로드 차단 중에도 QR·대화·조회·제어는 계속 통신합니다. 완전 오프라인/실차 오프라인 검증으로 표현하지 않습니다.

| 화면 | 역할 |
|---|---|
| 차량 `/mvp/car` | 주차 중 미연결 QR/코드 또는 운행 카드. 운행 마치기/계속 운행/기록 종료. 주행 중 빈 main, 음성 제어·입력 폼·팝업 없음 |
| 모바일 `/mvp/driver` | 기존 데모 직원/QR/해제 유지. 선택 직원의 진행·대기·수신 운행만 표시. 목적지·용도·상세 목적·거리·확인 필요 구분 |
| 관리자 `/mvp/admin` | 기존 연결 현황, 진행 운행·전송 대기/문제·실제 수신 목록 분리. 직원/부서/차량/시각/목적/거리와 수신본 집계 |
| 시연 패널 `/mvp/control` | 현재 서버 운전자·대화·안내, 모의 발화·확인/거절/보류·출발/도착·업로드 차단/복구, TTS와 자동 uploader |

## 시작과 정상 시연

설치된 Node24·Chrome·Playwright와 기존 의존성을 사용합니다. 프로젝트 루트에서:

```sh
npm run demo:mvp
```

터미널에 **실제 출력된** 시연 패널·차량·모바일·관리자 주소를 사용합니다. 매번 새 임시 DB·빈 포트이며 종료 후 데이터는 일회성입니다. 기존4000/5173 서버를 종료하지 않습니다. [QR 1단계](MVP_STEP1_QR.md)의 PC/휴대폰 주소 설정과 독립 컨텍스트 조건을 유지합니다.

1. 터미널에 실제 출력된 시연 패널·차량·관리자 주소를 독립 브라우저에서 엽니다. QR 링크 또는 코드 입력으로 데모 직원을 명시적으로 연결합니다.
2. 연결 직후에는 주차 대기 화면입니다. 출발 시각/거리를 만들지 않고 운행 마치기는 비활성입니다. 패널에서 시연 음성을 준비할 수 있습니다.
3. 패널의 **모의 출발**→**모의 도착**을 누릅니다. 주행 중 차량은 비워지고 도착 후 관측 거리가 표시됩니다. 아직 질문·이벤트·수신본은 없습니다.
4. 차량의 **운행 마치기**를 누릅니다. 후보 시각·거리를 고정한 뒤 패널에서 안내 완료→모의 발화→재확인 완료→모의 네를 전달하면 별도 저장 버튼 없이 자동 저장·전송됩니다.
5. **모의 나중에·무응답·실패**는 같은 후보의 목적 미확정 기록으로 저장·전송합니다. **계속 운행**은 후보·초안을 취소하되 같은 구간을 유지하고 주차 상태로 남습니다. 새 출발은 별도 모의 이벤트입니다.
6. **기록 종료**는 마지막 관측 경계의 미완료 구간만 미확정 보관하고 수집 세션을 끕니다. 빈 운행은 만들지 않습니다. 연결은 유지되며 새로고침으로 수집이 재개되지 않습니다. 주차 중 **기록 시작**이 필요합니다.
7. 진행 중 운행이 있으면 모바일 연결 해제는 차단됩니다. 먼저 차량에서 운행 마치기 또는 기록 종료를 진행합니다.

처음부터 다시 시연하려면 이번 터미널에 Ctrl+C 후 새 데모 서버·새 독립 브라우저로 엽니다. 기존 DB·브라우저 저장소를 지우는 초기화 API는 없습니다. 종료 시 이번 서버·직접 만든 임시 DB만 정리합니다.

## 음성 재생과 모의 입력

음성의 주체는 **시연 패널 한 곳**입니다. 모바일 QR 스캔이 다른 브라우저의 재생 허용을 뜻하지 않습니다. 준비 상태는 각 패널 문서의 메모리 상태이며 새로고침 뒤 자동으로 허가됐다고 복원하지 않습니다.

`speechSynthesis`·`SpeechSynthesisUtterance`로 한국어 합성을 요청하고 `onend`/`onerror`를 처리합니다. 사용할 수 없거나 차단·오류가 나면 이유를 표시합니다. 완료 이벤트가15초 안에 없으면 재생 요청을 취소하고 `playback-timeout` 실패로 처리합니다. 이15초는 시연용 timeout이며 차량 SDK 정책이 아닙니다. [Web Speech API](https://webaudio.github.io/web-speech-api/)의 합성 인터페이스를 사용하며 실제 recognition 객체·마이크 권한·외부 유료 API/키를 만들지 않습니다. 브라우저/OS의 합성 엔진·설치 음성·출력 장치는 별도 조건입니다.

**API 호출**, **브라우저 완료 이벤트**, **실제 소리 청취**는 다릅니다. 내부 `played`는 브라우저 `onend` 보고이며 발표자가 실제로 들었다는 인증이 아닙니다. UI도 ‘브라우저 완료 이벤트’로 안내합니다.

| 상태/조작 | 처리 |
|---|---|
| 준비하지 않음 | 질문 텍스트는 표시하지만 TTS를 자동 시작하지 않음 |
| 준비 완료 이벤트 | 현재 pending prompt의 서버 claim을 한 번 요청 |
| 다른 패널이 이미 claim | 같은 안내를 중복 재생하지 않음 |
| 재생 실패/미지원 | 오류 표시. 텍스트 확인 후 **안내 완료 모의** 또는 **모의 나중에** |
| 이미 요청된 안내에서 새로고침 | 자동 재생하지 않음. 필요하면 명시적 모의 완료 |
| 출발/해제/선택 차량 변경/패널 이탈·비활성/조회 실패 | 진행 음성 취소·늦은 콜백 적용 차단 |
| 다른 패널의 명시적 모의 완료 | 기존 재생을 취소하고 실제 완료로 다시 보고하지 않음 |

서버는 연결 ID·대화 ID·prompt ID·claim client ID·명령 ID와 현재 단계를 검증합니다. 오래된 완료/답변은 새 연결이나 다음 운행을 바꾸지 못합니다. 같은 명령 ID+같은 본문은 원래 결과를 반환하고 다른 본문은409입니다. 화면은 명령 응답을 가짜 성공값으로 저장하지 않고 공통 상태를 다시 조회합니다.

### 지원하는 발화 범위

규칙표에 정한 문장만 처리합니다. 예시는 업무 방문, 회사 출근/집 퇴근, 마트 장보기와 짧은 용도 표현입니다. ‘잠깐 나갑니다’ 같은 모호한 표현이나 지원하지 않는 문장은 초안을 임의로 만들지 않습니다. 목적지 없는 표현에는 목적지를 만들어 넣지 않습니다. 임의 문장을 이해하는 AI가 아닙니다.

모의 **네**만 확인 안내 완료 후 초안을 확정합니다. **아니요**는 초안 취소와 새 질문/대화로, **나중에·무응답**은 목적 미확정으로 바꿉니다. 중간 결과·침묵·재생 실패·시간 초과를 동의로 바꾸지 않습니다. 음성 기능이 실패해도 명시적 안내 완료 모의로 진행하거나 미확정 보관할 수 있습니다. 실패 자체도 미확정 보관 사유이며 동의로 처리하지 않습니다. 원음 파일은 저장하지 않습니다.

## 상태와 운전자 귀속

| 구간 | 상태 |
|---|---|
| 새 연결 | 주차 확인·수집 대기, 운행/질문 없음 |
| 모의 출발 | runtime `driving`, 같은 구간 수집, 화면 비움 |
| 모의 도착 | runtime `parked`, 거리 관측, 아직 종료/질문/이벤트 없음 |
| 운행 마치기 | `candidateEnd` 고정·`question` 생성 |
| 질문 실제/모의 완료 | `awaiting_answer` |
| 지원 모의 답변 | `confirmation`·미확정 초안 |
| 확인 안내 완료 | `awaiting_confirmation` |
| 모의 네 | 고정 후보+확인 목적 저장·queued·대화 `completed` |
| 모호한 답변/나중에/무응답/실패 | 목적 null로 저장·queued·`completed` |
| 계속 운행/재출발 | 초안·후보 취소, 같은 trip 시작 유지, 재출발 시 driving |
| 기록 종료 | 마지막 관측만 보관, 세션 false·연결 유지 |
| 실제 수신 commit | received trip·receipt, 해당 이벤트 `received` |

QR 연결과 출발은 다릅니다. **모의 출발은 명시적 개발용 조작**이며 실제 차량 신호가 아닙니다. 유효한 서버 연결이 있어야 출발하고 출발 때 companyId/employeeId/vehicleId/connectionId/conversationId/tripId·시각·모의 누적거리를 고정합니다. 화면의 계정 선택을 바꿔도 이미 시작한 운전자는 바뀌지 않습니다.

입력 중 재출발하면 질문/재확인·초안·종료 후보를 취소하고 같은 tripId·시작 시각·시작 누적거리로 이어갑니다. 모의 도착만으로 미확정 저장하지 않습니다. 운행 마치기 후 동의/보류/실패에서 확정하며, 그 다음 출발이 새 tripId를 생성합니다. 이전 목적을 복사하지 않습니다.

정상 모의 거리는 구간마다23,400m이며 같은 차량의 다음 누적거리는 직전 종료값에서 이어집니다. 시작/종료 원본은 나중의 대화 시간이나 재시도로 변하지 않습니다. 시각 역전 등 불완전 조건은 quality=`incomplete`로 구분하고 유효 거리 합계에서 제외합니다. 불명확한 거리를0으로 바꾸지 않습니다.

연결 해제는 대화를 취소하지만 종료된 전송 대기는 삭제하지 않습니다. 수신 검증은 **원래 수집 운행과 보존된 원래 연결**을 비교하며 현재 새 직원 연결을 이유로 과거 A의 이벤트를 버리거나 B로 바꾸지 않습니다.

## 전송·ACK·재시도

1. 사용자 동의/미확정 보관의 고정 후보 원본과 완성된 이벤트 문자열을 MVP 수집 DB에 같은 트랜잭션으로 보관합니다. 실패하면 active 운행과 원본을 유지하고 성공으로 처리하지 않습니다.
2. 패널 uploader가 `pendingUploads[].body`를 그대로 실제 HTTP로 보냅니다. 브라우저 새로고침 후에도 서버에 저장된 같은 ID·본문을 사용합니다. 단일 worker 내부에서 같은 이벤트를 겹쳐 보내지 않습니다.
3. ACK의 eventId·tripId·serverVersion1을 확인합니다. 관리자 수신 목록은 HTTP 요청 발송 여부가 아니라 **실제 수신 테이블**만 조회합니다. 수신 운행·영수증·수신 상태는 한 DB 트랜잭션입니다.
4. 응답 유실 후 동일 이벤트를 재전송하면 기존 영수증 ACK를 재사용합니다. 서버 상태 조회에서 이미 수신됐음을 확인한 경우에도 실제 receipt에 근거한 결과입니다.
5. 연결/일시 오류는 약1.5초 간격, 패널 실행별 이벤트당 최대5회 자동 시도합니다. 서버도 실패5회 후 `paused`로 보류합니다. 전송 차단 중에는 한 번의 실패 뒤 대기하고 복구 조작 시 재개합니다. transient queued/paused만 복구하며 blocked/conflict는 자동 해제하지 않습니다.
6. 잘못된 요청·충돌·잘못된 ACK는 반복 전송을 멈추고 본문을 보존합니다. 새로운 이벤트 ID나 추측 버전으로 우회하지 않습니다. 판별할 수 없는 transport 문제로 패널을 새로 연 경우 로컬 시도 횟수는 새로 시작할 수 있으나 서버의 blocked/conflict와 원본은 유지됩니다.

`active`, `queued`, `paused`, `blocked`, `conflict`, `received`는 서로 다릅니다. 모바일과 관리자는 목적 미확정·거리 불완전·전송 문제도 별도 사유로 표시합니다. 요약은 수신 건수, 수신본의 유효 거리 합계, 용도 미확정 수·거리 제외 수이며 승인/마감/신고 완료가 아닙니다.

## 새 API·데이터

기존 QR 경로는 유지하고 아래 MVP 경로만 추가했습니다. 기존 `/api/trip-events` 계약은 그대로입니다.

| API | 입력/역할 |
|---|---|
| GET `/mvp-api/state` | 기존 회사/직원/차량/연결 + `demoId`, `conversations`, `prompts`, `activeTrips`, `pendingUploads`, `receivedTrips`, `uploadBlockedVehicles`, `vehicleRuntime` |
| POST `/mvp-api/commands` | `{commandId,connectionId,type,conversationId?,value?,tripId?,promptId?}`. 대화는 정확한 conversationId 필요. 제어는 tripId/대화 snapshot 검증. depart/arrive/finish/continue/start_session/stop_session/unknown/park/answer/confirm/silence/failure/simulate_prompt |
| POST `/mvp-api/voice/claim` | `{promptId,clientId}` → `{claimed,prompt}` |
| POST `/mvp-api/voice/complete` | `{commandId,promptId,clientId,outcome:'played'|'failed'}` |
| POST `/mvp-api/vehicles/:id/upload-mode` | `{blocked:boolean}`. 운행 업로드만 차단/복구 |
| POST `/mvp-api/trip-events` | 준비된 `{schemaVersion:1,eventId,tripId,source:'mock',payload:trip}`. ACK `{eventId,tripId,serverVersion:1}` |

trip에는 원래 연결/회사/직원/차량/대화 ID, 시작/종료 시각·누적거리·거리, 목적지·용도·상세 목적·purposeConfirmed·quality·source가 있습니다. 수신본은 eventId/receivedAt/serverVersion을 더합니다. `pendingUploads`는 body 문자열·상태·시도 수·오류·다음 시각과 원본 trip을 보존합니다.

새 `mvp_conversations`, `mvp_prompts`, `mvp_trips`, `mvp_uploads`, `mvp_received_trips`, `mvp_trip_receipts`, `mvp_commands`, `mvp_workflow_meta`, `mvp_upload_modes`, `mvp_mock_odometers`, `mvp_vehicle_runtime` 테이블을 사용합니다. 기존 개발 DB를 마이그레이션하거나 여는 경로가 없습니다. `demoId`는 해당 임시 실행의 귀속 경계이며 새 데모 실행으로 이전 이벤트를 가져오지 않습니다.

## 다음 작업 인수인계

관리자 보완은 수신 운행의 원본/직원/연결을 보존하는 별도 보완 리비전으로 설계해야 합니다. 이번 MVP는 목적 미확정/불완전/전송 문제를 조회하지만 보완 요청 발송·승인·강제 수정은 없습니다. 다음 작업은 직원별 보완 권한·동시 수정/충돌·처리 이력을 먼저 정의합니다.

기간별 집계는 한국 날짜 경계와 수신본 범위·미수신/불완전 제외를 구분하고, 원본 시각·거리를 재계산하거나 운행을 임의 분할하지 않아야 합니다. 모의 세무처리는 실제 신고와 분리된 상태/문구로 추가해야 하며 현재 수신/동의를 신고 적격성이나 완료로 바꾸면 안 됩니다.

실제 STT·SDK·차량 자동 수집·운영 인증은 별도 검증 과제입니다. QR 선택은 실제 운전자 인증이나 운전 상태·마이크 권한을 증명하지 않습니다. 브라우저 TTS 호출/완료 이벤트·물리 음성 출력·실제 인식·SDK 데이터 수신을 계속 따로 기록해야 합니다.
